This directory contains contracts for sending and receiving cross chain messages that follows the TRC-7786 standard.

* {CrosschainLinked}: helper to facilitate communication between a contract on one chain and counterparts on remote chains through TRC-7786 gateways.
* {TRC7786Recipient}: generic TRC-7786 crosschain contract that receives messages from a trusted gateway.

Additionally there are multiple bridge constructions:

* {BridgeFungible}: Core bridging logic for crosschain TRC-20 transfer. Used by {BridgeTRC20}, {BridgeTRC7802} and {TRC20Crosschain},
* {BridgeNonFungible}: Core bridging logic for crosschain TRC-721 transfer. Used by {BridgeTRC721} and {TRC721Crosschain},
* {BridgeMultiToken}: Core bridging logic for crosschain TRC-1155 transfer. Used by {BridgeTRC1155} and {TRC1155Crosschain},
* {BridgeTRC20}: Standalone bridge contract to connect a TRC-20 token contract with counterparts on remote chains,
* {BridgeTRC721}: Standalone bridge contract to connect a TRC-721 token contract with counterparts on remote chains,
* {BridgeTRC1155}: Standalone bridge contract to connect a TRC-1155 token contract with counterparts on remote chains,
* {BridgeTRC7802}: Standalone bridge contract to connect a TRC-7802 token contract with counterparts on remote chains.

import "@openzeppelin/tron-contracts/crosschain/CrosschainLinked.sol";

Core bridging mechanism.

This contract contains the logic to register and send messages to counterparts on remote chains using TRC-7786
gateways. It ensure received messages originate from a counterpart. This is the base of token bridges such as
{BridgeFungible}.

Contracts that inherit from this contract can use the internal {_sendMessageToCounterpart} to send messages to their
counterpart on a foreign chain. They must override the {_processMessage} function to handle messages that have
been verified.

=== `++TRC7786Recipient++` link:https://github.com/OpenZeppelin/tron-contracts/blob/v5.7.0/contracts/crosschain/TRC7786Recipient.sol[{github-icon},role=heading-link]

[.hljs-theme-light.nopadding]
```solidity
import "@openzeppelin/tron-contracts/crosschain/TRC7786Recipient.sol";
```

Base implementation of a TRC-7786 compliant cross-chain message receiver.

This abstract contract exposes the `receiveMessage` function that is used for communication with (one or multiple)
destination gateways. This contract leaves two functions unimplemented:

* {_isAuthorizedGateway}, an internal getter used to verify whether an address is recognised by the contract as a
valid TRC-7786 destination gateway. One or multiple gateway can be supported. Note that any malicious address for
which this function returns true would be able to impersonate any account on any other chain sending any message.

* {_processMessage}, the internal function that will be called with any message that has been validated.

TRC-7786 requires the gateway to ensure messages are not delivered more than once. Therefore, we don't need to keep
track of the processed receiveId.

=== `++BridgeFungible++` link:https://github.com/OpenZeppelin/tron-contracts/blob/v5.7.0/contracts/crosschain/bridges/abstract/BridgeFungible.sol[{github-icon},role=heading-link]

import "@openzeppelin/tron-contracts/crosschain/bridges/abstract/BridgeFungible.sol";

Base contract for bridging TRC-20 between chains using a TRC-7786 gateway.

In order to use this contract, two functions must be implemented to link it to the token:
* {_onSend}: called when a crosschain transfer is going out. Must take the sender tokens or revert.
* {_onReceive}: called when a crosschain transfer is coming in. Must give tokens to the receiver.

This base contract is used by the {BridgeTRC20}, which interfaces with legacy TRC-20 tokens, and {BridgeTRC7802},
which interface with TRC-7802 to provide an approve-free user experience. It is also used by the {TRC20Crosschain}
extension, which embeds the bridge logic directly in the token contract.

==== `[.contract-item-name]#++_onReceive++#++(address to, uint256 amount)++` [.item-kind]#internal#

"Unlocking" tokens is done by releasing custody.

Uses {SafeTRC20-safeTransferChecked} rather than {SafeTRC20-safeTransfer} so the release path also works
for tokens such as TRON USDT (`TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`) whose `transfer` returns `false` on a
*successful* transfer. {safeTransfer} reverts on such a token; because locking via {_onSend}
(`transferFrom`, which USDT returns `true` for) still succeeds, that would let deposits through while
permanently trapping every withdrawal in the bridge. {safeTransferChecked} verifies success by the calling
contract's (sender's) balance delta and works whether the token returns `true`, `false`, or nothing.

NOTE: This custodial bridge assumes a token that is neither rebasing nor fee-on-transfer — not because of
{safeTransferChecked} (which tolerates fee-on-transfer), but because taking custody in {_onSend} credits
the full `amount` while the contract would actually receive less, breaking release accounting. Such tokens
must not be bridged through this contract.
